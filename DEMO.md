# Demo runbook

The version that ships is `main`. Rehearse on the `demo` branch.

## Before the demo

```bash
git switch main
cd integration
docker compose up -d --build --wait
```

Confirm all three services are up:

```bash
curl http://localhost:8000/health     # database: up, ai_service: up
curl http://localhost:8001/health     # model_loaded: true
```

Open <http://localhost:5173> once and leave the tab. A cold Vite build takes a
few seconds and is the most likely thing to go wrong in a room with bad wifi.

## The run, in order

This is roughly four minutes and shows a complete story rather than a feature
list.

**1. The system is healthy.** Point at the status bar. Backend up, database up,
AI service up. Mention that the AI service is optional and the backend degrades
gracefully — you will demonstrate that in step 5.

**2. A good part.** Fill the form with in-spec numbers:

| Field                    | Value |
| ------------------------ | ----- |
| Part serial              | DEMO-001 |
| Part name                | Drive Shaft |
| Inspector                | your name |
| Dimension deviation (%)  | 0.3 |
| Surface roughness Ra     | 0.5 |
| Torque (Nm)              | 15 |
| Temperature (C)          | 30 |
| Vibration (mm/s)         | 0.8 |
| Cycle time (s)           | 14 |

Submit. It comes back `Minor` / `Passed` with a confidence percentage. Say the
one-to-one mapping: severity comes from the model, status is derived from it.

**3. A bad part.** Same form, different serial and much worse numbers:

| Field                    | Value |
| ------------------------ | ----- |
| Part serial              | DEMO-002 |
| Dimension deviation (%)  | 12 |
| Surface roughness Ra     | 18 |
| Torque (Nm)              | 280 |
| Temperature (C)          | 150 |
| Vibration (mm/s)         | 35 |

Submit. It comes back `Critical` / `Failed`. Point out that only one of these
six readings being extreme is enough to escalate — that was the interesting
modelling problem.

**4. The dashboard.** The summary cards now show the severity mix and the
critical rate. Filter by `critical`; the table narrows to DEMO-002. Expand
**Details** to show the full measurement set behind the verdict.

**5. Resilience.** This is the part that distinguishes the project. Stop the AI
container:

```bash
docker compose stop ai
```

Submit a third inspection. The record still saves, the UI says the AI service
was unavailable, and the status is `Pending`. Restart it:

```bash
docker compose start ai
```

Press **Re-predict** on that record. It is graded normally. Nothing was lost and
the inspector never lost their work to an outage.

**6. The tests.** If there is time:

```bash
cd ai        && pytest -q          # 31
cd backend   && pytest -q          # 33
cd frontend  && npm test           # 33
cd integration && pytest           # 9
```

106 checks. The interesting design note: the backend's 33 tests never start the
model, because the AI client is injected and stubbed. That is why they run in
under a second and never flake.

## Likely questions

**Why logistic regression and not a random forest?**
Severity is a weighted sum of measurements normalised against their reference
limits, so it is a linear function of those ratios and linear decision boundaries
are the right fit. The forest scored 87% against 99% and, more importantly, was
unstable near the thresholds — it read a single severe measurement surrounded by
nominal ones as merely "major".

**Is the training data real?**
No, it is synthetic and generated by a documented rule in `ai/app/data.py`. The
rule encodes domain knowledge, the model learns to reproduce it, and the real
value is that the service is wired end to end. Swapping in real measurements
means replacing one function.

**What happens if the database is down?**
`/health` reports `degraded` and the record is not written. That is the one
failure we do not paper over, because losing an inspection silently is worse
than refusing it.

**How do you know the branches helped?**
Each developer owns one directory, so the three component branches touched
disjoint paths and the `integration` merge completed with zero conflicts. The
merge graph in `git log --graph --oneline --all` shows the staged flow.

## If something breaks

| Symptom                                | Fix |
| -------------------------------------- | --- |
| Frontend loads, "Backend unreachable"   | `docker compose logs backend` |
| Backend healthy, `ai_service: down`     | `docker compose up -d ai` and wait for the health gate |
| AI container restarting                 | it is training a model on first start; give it ~20s |
| Port already in use                     | a service is running outside compose; `docker compose down` first |
| Database looks empty                    | `docker compose down -v` clears the volume, then bring it up again |
